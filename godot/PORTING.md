# Porting Banner & Blade to Godot

The TypeScript game in `../game` is the **specification**. The Godot build is
the same game: same rules, same numbers, same screens, same feel. Port; don't
redesign. When the TS code does something odd, the port does the same odd
thing (and keeps the comment that explains why).

Godot 4.7, GDScript, GL Compatibility renderer (runs everywhere, exports to
the web so the fly.io site keeps working).

## Layout

`game/src/<dir>/<file>.ts` → `godot/src/<dir>/<file>.gd` (snake_case file
names, same directories). One TS module = one GDScript file with a
`class_name` (PascalCase of the file: `skirmish_ai.ts` → `SkirmishAI`,
`math.ts` → `MathU`, `types.ts` → `T`). Top-level TS functions become
`static func`; module constants become `const` (or read from `C`, below).
A TS class becomes the file's class (`extends RefCounted`).

- `godot/data/content.json` (+ `content.f64`): every plain-data constant from
  the TS content modules, exported by `game/scripts/export_godot_data.ts`.
  **Re-run it** whenever TS content changes. Never hand-copy content numbers.
- Autoload `C` (`src/autoload/c.gd`, generated): `C.UNITS`, `C.BUILDINGS`,
  `C.AGES`, `C.TILE`, `C.SIM_HZ`, `C.FACTIONS`, `C.OATHS`, `C.DIFFICULTIES`,
  `C.PAL`, … — same names as the TS exports. `C.mod("content/units")` gives a
  whole module. Data that is a *function* in TS (an Oath's `apply`, a boon's
  `lines`, factions' helpers…) is not in the JSON — port those functions by
  hand into the matching `src/content/<module>.gd` (the exporter lists them in
  `content.json._functions`).
- `src/engine/js.gd` (`JS`): JavaScript number semantics. **Use it.**
- `src/sim/types.gd` (`T`): enums. `src/sim/entity.gd` (`Entity`),
  `src/sim/order.gd` (`Order`).
- `tests/`: `test_*.gd` files (extend `TestCase`), run by
  `godot --headless --path godot res://tests/run.tscn [-- test_name ...]`.
  Fixtures from the TS build: `tests/fixtures/*.json`, regenerated by
  `game/scripts/godot_parity.ts`.
- After adding or renaming any `class_name`, rebuild the class cache:
  `godot --headless --path godot --editor --quit` (otherwise "Could not find
  base class"/"Identifier not found").

## Names

Keep every TS identifier **verbatim** — fields, methods, locals, constants
(`issueMove`, `buildState`, `popCap`, `SIM_DT`). camelCase is fine in GDScript
and it makes the port diffable line by line against the spec, and lets modules
ported by different people call each other by the names the TS uses.
Exceptions only where GDScript forbids the name: `int`→`int_`, `bool`→`bool_`
(e.g. `rng.int_(a, b)`), `range` is fine as a method, `class`→`klass`,
`func`→`fn`, `signal`→`signal_`, `in`→`in_`, `var`→`var_`, `match`→`match_`,
`self`→`me`, `name` is fine as a var. Keep TS enum member names
(`T.OrderKind.Gather`, `T.Kind.Unit`, `T.BuildState.Done`).

## Numbers — where determinism lives

The simulation must produce the same result as the TS build from the same seed
(lockstep multiplayer and replays depend on it, and the parity tests check it).

- JS numbers are 64-bit doubles. Use `float` for anything arithmetic, `int`
  only for ids, counts, indices, enum values, bitmasks.
- **Division**: `int / int` truncates in GDScript. If either side might be an
  int, write `float(a) / b`. Never introduce integer division the TS didn't have.
- **No `Vector2` in the sim** (it is 32-bit). Scalars only. Vector2 is fine in
  rendering/UI.
- `Math.round(x)` → `JS.round(x)` (GDScript's `round` differs on negative
  halves). `Math.floor` → `floor` (float) / `floori`. `Math.hypot` →
  `JS.hypot` (bit-exact V8). `Math.sign` → `JS.sign`. `a % b` on floats →
  `fmod(a, b)`. `Math.min/max` → `minf/maxf` (or `min/max` for ints).
  `Math.trunc` → `JS.trunc`. `x | 0`, `>>> 0`, `Math.imul` → `JS.i32`,
  `JS.u32`, `JS.imul`, `JS.ushr`.
- **Sorting**: `arr.sort(cmp)` in JS is stable; Godot's `sort_custom` is NOT.
  Always `JS.sort_by_cmp(arr, func(a, b): return <number>)` (same comparator
  as the TS) or `JS.stable_sort(arr, less)`.
- Float literals with more than 15 significant digits are parsed inexactly by
  GDScript; compute them instead (`PI`, `TAU`, `1.0/3.0`).
- JSON numbers from `C` are floats (as in JS). Cast `int(...)` to index.
- Iteration order matters: JS objects/Maps/Sets iterate in insertion order,
  and so do GDScript Dictionaries — keep the same insertion order. (JS objects
  put integer-like keys first, ascending; mind it if a TS object is keyed by
  numbers.)
- `Math.random()` never appears in the sim; the sim uses its `RNG`.

## Translating TS constructs

- Object literals / interfaces with a fixed shape that the sim reads hot
  (PlayerState, stats) → small classes with typed fields. Records keyed by
  strings (`Record<string, number>`, `trainedByType`) → `Dictionary`.
  `Set<string>` → `Dictionary` used as a set (`d[k] = true`, `d.has(k)`).
- Optional fields on content (`def.pierceArmor ?? def.armor`) → `JS.opt(def,
  "pierceArmor", def.armor)` or `def.get("pierceArmor", ...)`. A missing key
  read with `def.key` is an error in GDScript, where TS gives `undefined`.
- `?.` / `??` → explicit null checks.
- Arrow functions → lambdas. **GDScript lambdas capture locals by value**: a
  closure that assigns to an outer `let` does nothing outside. Box it
  (`var n := [0]` … `n[0] += 1`) or restructure.
- Array methods: `filter/map/any(some)/all(every)/reduce/find` → GDScript
  equivalents (`find` → loop or `filter(...).front()`; mind empty arrays).
  `arr.length` → `arr.size()`. `push` → `append`. `splice` → `remove_at` /
  `slice`. `includes` → `has`. `[...a]` → `a.duplicate()`.
- Template strings → `"%s ... %d" % [...]` or concatenation; number to text
  like JS (`${n}`) → `JS.num(n)`; `toFixed` → `JS.to_fixed`;
  `toLocaleString("en-GB")` → `JS.locale_int`.
- `localStorage` → `Storage` autoload (user:// JSON) once it exists.
- Classes with `private`/`readonly`: just vars (prefix nothing; keep names).
- Getters (`get armySize()`) → `func armySize()`… but then callers must use
  `armySize()`; or a GDScript property with `get:`. Prefer the property form
  (`var armySize: int: get = _get_armySize`) so call sites read the same.

## Rendering and UI

The TS draws everything immediate-mode on a 2D canvas each frame (world,
HUD, menus). The port keeps that structure: a `Ctx` class (canvas
compatibility layer: `fillStyle`, `beginPath`, `arc`, `fill`, `fillText`,
gradients, `save/restore`, transforms…) draws through a `CanvasItem` in
`_draw()`, and the `ui` immediate-mode helpers (button/panel/text/bar/…) sit on
top, so screens port line by line. Fonts: SystemFont (Trebuchet MS / Georgia
as in the browser, with fallbacks). Performance work (caching unit art to
textures, batching) happens under that layer, not by changing the screens.

## Done means

Ported, compiles without errors (warnings ok), and has tests: parity tests
against the TS fixtures where the TS is deterministic, and unit tests ported
from the module's `*.test.ts` where they exist (port the important ones).
